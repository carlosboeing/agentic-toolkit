# `/start-research`

Investigate a bounded question before, during, or independently of other lifecycle work. Research supplies evidence, not approval of product scope.

## Synopsis

```text
/start-research [question or source-path]
/start-research help
```

If the entire argument is `help`, `--help`, `-h`, `?`, or `usage`, or such a token follows a source path, show this synopsis and stop. The same words inside the question are content.

## Procedure

1. Read the question and named sources. Without a clear question, discover relevant project context and ask only for the consequential missing scope. Identify the decision the evidence supports, uncertainty, expected depth, and a stopping condition. Enough evidence for that decision is sufficient; report gaps instead of implying exhaustive coverage.
2. Discover relevant available skills, connectors, search, browser, experiment, and computer-use capabilities. Read applicable tool instructions. Use an explicitly requested specialist method; `deep-research` can supply a comprehensive multi-source method when its scope, facilities, and delegation are applicable. No background agent or parallel work is required. Delegate only within actual authorization and available facilities; otherwise work serially.
3. Use the least access sufficient. Prefer primary evidence such as official documentation, specifications, source code, or first-party data. Trace consequential claims to the owning source and distinguish observation, inference, and uncertainty. Verify facts that can change and record dates or revisions where useful. Interviews and experiments can supply evidence when their scope is authorized.
4. When no account is needed, prefer an isolated browser session. Access to the user's authenticated profile or desktop needs explicit authorization unless already granted for this scope. Posting, purchasing, installing, or a spike with writes or external effects needs its own bounded authorization. A read permission grants no blanket action permission. If a capability is missing, explain the evidence gap and request only the additional access needed.
5. Synthesize findings, alternatives, limitations, and implications for the original question. Save a report when requested or when decisions, review, or recovery warrant it; otherwise respond in chat. Cite sources beside claims and link to the work they inform. Do not create a mandatory research phase or document before design.

## Context and boundaries

Use project conventions for storage, metadata, review, and Git actions. Discover actual locations and types, including legacy layouts. On resume, reconcile source revisions, Git state, checkpoints, and authority.

Read original product and architecture sources and relevant prior lessons. For substantial work, retain stable consequential references and account for preserved obligations, authorized changes, reasoned exclusions, and unresolved decisions. Reconcile source differences with affected work and reviews; block unresolved or unauthorized consequential changes. Keep scope, authority, verified progress, evidence, unresolved decisions, and next checkpoint visible in existing records.

Stop at a phase-only boundary. Explicit autonomous scope can include transitions and delegated reviews; record its scope, retained human gates, and endpoint once when recovery needs it. Stop at retained human gates or consequential choices outside that scope. Agent review never proves personal human approval, and status alone grants no authority. External effects follow actual authorization.

Capture reusable lessons with context, evidence, workaround and result, and confirmed cause or uncertainty, in an existing record or a standalone file when useful. Avoid logging every transient error. End with the outcome, material gaps, and next step. Recommend the same or a fresh session, and human or independent review, when context and consequence warrant it. Recommendations authorize no later phase.
